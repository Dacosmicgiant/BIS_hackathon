## What It Does

Converts a plain-language product description into precise BIS standard recommendations in under 100ms.

**Input:**
> *"We manufacture 33 grade ordinary Portland cement for construction use"*

**Output:**
```
1. IS 269 : 1989  — Ordinary Portland Cement, 33 Grade
   ↳ This standard directly governs your 33 grade OPC product, covering all
     chemical composition and physical performance requirements.

2. IS 8112 : 1989 — 43 Grade Ordinary Portland Cement
3. IS 12269 : 1987 — 53 Grade Ordinary Portland Cement
...
```

Plus an exportable PDF compliance report.

## Architecture

```
Product Description
        ↓
  Query Validator
  (Gemini Flash Lite — rejects non-product queries)
        ↓
   ┌─────────────────────────────────┐
   │         Hybrid Retriever        │
   ├──────────────────┬──────────────┤
   │  Dense Search    │ Sparse Search│
   │  BGE-small-en    │  BM25Okapi   │
   │  ChromaDB        │  rank-bm25   │
   └──────────────────┴──────────────┘
        ↓ Reciprocal Rank Fusion (RRF)
   Top 5 Candidates
        ↓
   Rationale Generator
   (Gemini Flash Lite — one sentence per standard)
        ↓
   FastAPI → React UI + PDF Export
```

### Why Structured Parsing Over Chunking

Most RAG systems split documents into 512-token chunks. We don't.

Every standard in SP 21 is parsed into a typed JSON object:

```json
{
  "is_code":        "IS 269 : 1989",
  "title":          "ORDINARY PORTLAND CEMENT, 33 GRADE",
  "section_number": 1,
  "section_name":   "Cement and Concrete",
  "subcategory":    "Cement",
  "scope":          "Covers the manufacture and chemical and physical requirements...",
  "keywords":       ["portland", "cement", "33", "grade", "opc", ...],
  "year":           1989,
  "raw_text":       "..."
}
```

**Why this matters:**
- IS codes live in metadata — never generated by LLM, never hallucinated
- No standard ever split across chunks — full context preserved
- Enables metadata filtering before semantic search
- Foundation for future revision tracking and dependency mapping

## Tech Stack

| Layer | Tool | Purpose |
|---|---|---|
| PDF Parsing | pdfplumber | Extract structured standard objects from SP 21 |
| Embeddings | BAAI/bge-small-en-v1.5 | Dense semantic vectors |
| Vector Store | ChromaDB | Persistent cosine similarity search |
| Sparse Search | rank-bm25 (BM25Okapi) | Exact keyword + IS code matching |
| Fusion | Reciprocal Rank Fusion | Combine dense + sparse rankings |
| LLM | Gemini 2.0 Flash Lite | Query validation + rationale generation |
| Backend | FastAPI | REST API server |
| Frontend | React + Tailwind | UI with rationale toggle + PDF export |
| PDF Export | ReportLab | Compliance report generation |

### 1. Clone and create environment

```bash

cd BIS_copilot

python3 -m venv .venv
source .venv/bin/activate        # Linux/Mac
# .venv\Scripts\activate         # Windows

pip install -r requirements.txt
```

### 2. Configure environment

```bash
cp .env.example .env
```

Edit `.env`:
```
GEMINI_API_KEY=your_gemini_api_key_here
```

### 3. Place the dataset

```
data/
└── SP21.pdf    ← place BIS SP 21 : 2005 PDF here
```

### 4. Build the index

This is a one-time step. Run in order:

```bash
# Step 1 — Parse PDF into structured standard objects
python3 src/parser.py
# Output: data/standards.json (566 standards)

# Step 2 — Build vector + BM25 index
python3 src/indexer.py
# Output: index/chroma/, index/bm25.pkl, index/lookup.json
```

Expected output for parser:
```
✓ All 10 public test standards found
Scope coverage: 566/566
Section distribution: 27/27 sections
```

Expected output for indexer:
```
✓ ChromaDB index built: 566 documents
✓ BM25 index saved
Smoke test: 3/3 queries ✓
```

## How the Pipeline Works

### 1. Parsing (`parser.py`)

State-machine parser walks the PDF page by page, detecting:
- `SUMMARY OF` headers to start a new standard
- IS code patterns including multi-part standards (`IS 2185 (Part 2) : 1983`)
- Multi-line titles
- Scope text across 6 different formatting variants
- Section and sub-category headers

Handles SP 21's two-column layout by collecting scope text line-by-line until a clause boundary is hit.

### 2. Indexing (`indexer.py`)

Two parallel indexes built from `standards.json`:
- **ChromaDB** — each standard embedded with `BAAI/bge-small-en-v1.5`, stored with full metadata
- **BM25** — tokenized corpus stored as `bm25.pkl` for exact keyword matching
- **Lookup map** — `lookup.json` for O(1) standard retrieval by IS code

### 3. Retrieval (`retriever.py`)

For each query:
1. Embed query with BGE-small → top 20 from ChromaDB (cosine similarity)
2. Tokenize query → top 20 from BM25
3. Fuse both ranked lists with RRF (k=60)
4. Return top 5 standard objects

### 4. Pipeline (`pipeline.py`)

Two modes:
- **`recommend_codes_only()`** — pure retrieval, no LLM, ~50ms (used by `inference.py`)
- **`recommend()`** — validates query with Gemini, retrieves, generates rationale per standard

### 5. Export (`exporter.py`)

ReportLab generates a structured PDF with:
- Summary table of all recommended standards
- Detailed profile card per standard (rationale + scope + metadata)
- Branded header/footer
